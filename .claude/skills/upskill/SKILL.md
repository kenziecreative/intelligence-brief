# /upskill — Constraint Audit of a Plugin's Instruction Surfaces

Audit a plugin's instruction surfaces for anything that would constrain a highly capable
model into producing subpar results. Assume the model executing the plugin is
intelligent, holds the whole job, and keeps getting smarter. The question is never
whether the work deserves a big model — it is whether the instructions get in the
model's way. A skill should define the job and the method; it should not manage the
worker.

## Two grains

- **Surface audit** — `/upskill <plugin> <skill|command|agent name>` (or a path). The
  primary unit: one surface plus everything it loads and everything that gates it (see
  inventory below), plus a seam check of its blast radius. Resolve names against the
  plugin's `skills/`, `commands/` (commands nest — walk recursively), and `agents/`
  dirs; if ambiguous, say what matched and ask.
- **Plugin audit** — `/upskill <plugin>`. An orchestration, not one undifferentiated
  read: inventory every surface, audit each on its own, then run an **integration
  pass** over the cross-surface seams. Independent surface audits may run as parallel
  subagents; the integration pass needs all of them.

With no argument, ask which plugin or surface.

**Verdicts are scoped and worded so they can't be mistaken.** A surface audit may say
"clean within its dependency closure"; it may never speak for the plugin. A plugin
verdict requires every surface section to be current (see staleness, below) and the
integration pass to have run.

**Rewrites are always plugin-scoped**, whatever the audit grain — versioning, mirrored
contracts, and the regression net belong to the plugin as a whole.

## Inventory: reachability, not a glob

A surface is everything that shapes the model's behavior at runtime, found by starting
at the entry file and following every load:

- **Instruction text** — SKILL.md, `references/` and bundled docs it points at,
  `commands/**/*.md`, `agents/*.md`, shipped templates that instruct agents (e.g.
  `templates/CLAUDE.md`), and prompt text embedded in or generated by scripts.
- **Execution settings** — frontmatter `model:` pins, `allowed-tools`, hooks that
  inject text or block actions, agent dispatch rules, budget and permission flags.
  The model never reads these, but they cap it all the same. A `model:` pin to an
  older model is the purest capability fossil: a standing claim that the current
  model can't be trusted with the job.
- **Evidence, not targets** — the root and plugin `AGENTS.md` and any
  `dev/<plugin>/` architecture docs. Read them for ownership, mirrored contracts,
  and rule provenance; audit them only if explicitly asked.

List exclusions and anything unreadable in the report. An unread file is an uncovered
claim, not a silent pass.

## Seam check (part of every surface audit)

Before ruling on a surface, sweep its blast radius: wrappers and commands that invoke
it, surfaces that mirror the same rule, state files it reads or writes and their other
readers and writers, parsers/validators/hooks that enforce its outputs, and eval
expectations that encode its behavior. A rule cut in one place but alive in a mirror
is not cut — the mirror either moves with it or the finding says so.

## The central test

Sort every instruction into one of two piles.

**Intent constraints — keep.** They encode what the author wants: the outcome, voice
and style rules, scope boundaries, safety and credential rails, human gates on
irreversible or judgment-owned steps, evidence standards, the review bar. They would
still be the right instruction on a model twice as capable.

**Capability constraints — cut.** They encode what the author believed the model
couldn't do: chunking and do-it-in-parts, re-read/re-paste rituals, mandated sequence
where order doesn't serve the outcome, forced mid-task check-ins the user never asked
for, verify-every-line hedging, "present options, don't decide" where a decision is
wanted, rigid templates standing in for trust, expert-persona incantations, model
pins to superseded models, and fossilized workarounds for a past model's failure
mode. Remove these outright — translating them preserves the ceiling.

**Every finding carries a source label**, because "not capability" has more than one
cause: `user-intent` / `product-method` / `safety-governance` / `external-contract` /
`capability-workaround`. Only the last is cut on capability grounds. External
contracts — schema and parser expectations, surface limitations (e.g. Cowork's
no-JS/no-shell rules), tool permissions, marketplace workarounds like the
version-prefix duplication — do not dissolve on a smarter model: keep them, name the
contract they serve, and note what would have to change for the rule to go.

**Method is intent — the rule that matters most in this repo.** These plugins are
deliberately process-shaped products: staged arcs, blind runners, audit gates,
non-invention rules. A stage sequence, gate, or evidence discipline that *is the
product's method* sorts as intent, even when it looks like scaffolding. The capability
tell is an instruction aimed at the *model's execution* rather than the *method's
definition*: "process the transcript in three passes" is capability; "drafts never
skip the audit gate" is method. And distrust of stochasticity is not distrust of
capability — independent review, multi-sampling, and deterministic gates counter
randomness and grader leniency, not low intelligence; they stay valuable on any model.

**Rulings:** keep / cut / rewrite as intent / **move to mechanism**. The fourth is for
prose that is really a contract: its enforcement belongs in deterministic machinery —
a schema check, a validator script, a hook — not in instructions the model must
remember. Name the mechanism (this repo's `check-version-prefix.mjs` is the pattern).

**Hard cases.** Run the upgrade-survival test: would this line still make sense on a
much smarter model? Check the fossil record — the plugin's CHANGELOG and `git log`
often say why a rule was added; a rule born from a specific model failure is a
candidate fossil, but confirm the failure couldn't recur before cutting a rule that
guards against it. If a line still won't sort, ask the user why it exists. Never
guess. Tag each finding's evidence basis: observed / history-backed / inferred /
unresolved.

## Watch for the twin failure

Over-constrained skills are usually under-specified underneath: rich in process, poor
in intent. Wherever you cut scaffolding, check whether the outcome, boundaries, and
quality bar it was compensating for are actually stated. Flag what's missing; propose
fills as labeled suggestions, never as fact.

## Output

Write `dev/<plugin>/constraint-audit.md`, **organized as one section per surface**.
Scoped runs merge, full runs replace: a surface audit rewrites only its own section
and refreshes the verdict; a plugin audit overwrites the whole file. It stays a
snapshot, not a log. For a target outside any plugin, present the report in
conversation.

* **Provenance header** — audit date, commit (note a dirty worktree), scope of this
  run, surfaces inventoried, references followed, exclusions and unreadable files.
  A clean audit still writes all of this: "clean" is a claim about covered scope,
  and the header is what makes it checkable. Do not manufacture findings to look
  thorough.
* **Verdict** — one honest, scope-worded line at the top.
* **Per-surface sections** (each recording the commit it was audited at — staleness
  is checked against git, not hand-maintained stamps: a surface that changed since
  its section's commit is stale, and a plugin verdict may not rest on it):
  * **Findings** — the quoted line with `file:line`, source label, pile, evidence
    basis, and ruling with one sentence of reasoning. A repeated instruction family
    may be grouped into one finding that lists every affected `file:line` — group,
    never omit. Cover keeps as well as cuts.
  * **Proposed rewrites** — paste-ready and model-agnostic: no model names, no
    capability assumptions in either direction.
  * **Still under-specified** — intent the original never stated, one question per gap.
* **Cross-surface findings** — plugin audits write this from the integration pass:
  contradictions between surfaces, contracts duplicated with drift, rules mirrored in
  templates or eval expectations. Surface audits record what the seam check turned up
  here too.

## Applying rewrites

Audit-only is the default. Apply edits only when the user asks, and then — always at
plugin scope:

1. **Baseline first.** If the plugin has an eval pack (`eval/targets/<plugin>/`), run
   `/eval-run` before editing (or identify a current green iteration) so post-edit
   results have a comparison.
2. **Impact note per rewrite**, before touching files: the intent preserved, the
   assumption removed, and every mirror, template, generated artifact, or
   parser/state dependency the seam check says must move with it. Apply mirrors
   together — never leave a contract half-cut.
3. Follow the release loop in the root `AGENTS.md` — version bump, both description
   prefixes, CHANGELOG, README table, AGENTS list, `check-version-prefix.mjs`,
   `claude plugin validate`.
4. **Re-audit the changed surfaces** — the rewrite must itself pass this skill's test —
   and re-run `/eval-run`.
5. **A red golden is a signal to triage, not a verdict.** Check in order: pre-existing
   in the baseline? sampling variance (compare the multi-sample spread)? an unrelated
   worktree change? a stale rubric or gate that encodes the very fossil just removed?
   or a real regression? Only a real regression restores the rule — and restore it as
   intent, stating what it protects. A stale eval expectation changes only by an
   explicit, recorded product decision — never by silent test accommodation.
6. Record in the audit file which rewrites the user accepted, rejected, or deferred.
7. **No eval pack** → say plainly that behavioral verification is absent; offer a
   targeted runtime scenario, or mark the rewrite behaviorally unverified.

## Guardrails

- Never cut an intent constraint because it's inconvenient. Voice rules, boundaries,
  credential hygiene, non-invention rules, and human gates are the author's.
- **Autonomy check:** cutting a check-in or approval step must not silently broaden
  what the plugin writes externally, its permissions, or the judgment it owns. If a
  cut moves a decision from the user to the model, surface that and get an explicit
  yes.
- Never file an external contract as a capability workaround — smarter models don't
  dissolve schemas, surfaces, or permissions.
- Never audit files you haven't read, and never invent outcomes or standards the
  author didn't state.
- Rewritten surfaces must survive a model upgrade with zero edits. If a proposed line
  wouldn't, it doesn't ship.
- Verdict honesty: a surface verdict never reads as a plugin verdict.
- This skill's own text is subject to its own test.
